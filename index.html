01페달 오조작 방지 보조 시스템

팀 프로젝트 · 대표

페달 입력으로 오조작을 판단해 모터를 멈추는 차량 보조 시스템을 모형 차로 구현

기간약 1.5개월 (~2024.12)
인원6명
역할전·후방 보드 담당
환경TOPST D3 · Cortex-R5 FreeRTOS

시스템 구성

페달 입력→중앙 보드 · 오조작 판단→ UART →전·후방 보드 (담당)→모터

담당 업무

  • Cortex-R5 FreeRTOS에서 초음파 센서·모터 Task와 오토홀드 기능을 C로 구현
  • 하드웨어 타이머 Free-run 카운터로 Echo 펄스 폭을 재서 거리 측정
  • 5V Echo를 3.3V GPIO에 맞추는 저항 분배 회로 설계·배선
  • 중앙 보드의 오조작 판단 결과를 UART로 받아 모터 제어
  • 전·후방 보드 아키텍처 설계, 요구사항 정의서, 단위·통합 테스트

결과

  • 2024.12.18 최종 시연에서 의도대로 동작
  • 중앙 보드의 오조작 판단을 UART로 받아 실제 모터를 정지

트러블슈팅

측정 거리가 실제의 2배로 나오던 문제
문제 계산한 거리가 실제 거리의 약 2배. 코드를 고쳐도 해결되지 않음
원인 매뉴얼에서 타이머 클럭을 확인하니 24MHz를 12분주해 1 Tick = 0.5µs였는데, 1µs로 계산하고 있었음
해결 Tick → 시간 변환식을 실제 클럭 기준으로 수정
결과 종이에 5·10·15·20·25·30cm를 표시해 거리마다 실측 비교, 측정값이 실제 거리와 일치
5V 센서 출력과 3.3V GPIO의 전압 차이
문제 초음파 센서 Echo는 5V, SoC GPIO는 3.3V
해결 저항 분배 회로로 전압을 낮춰 GPIO에 연결

배운 점

코드 바깥의 하드웨어 설정이 결과를 좌우하고, 보드끼리 약속한 데이터 형식이 정확히 지켜져야 하나의 시스템이 된다는 것을 배웠습니다.

02DisplayPort 커널 드라이버 분석 및 재연결 오류 수정

개인 프로젝트 · Linux 커널

DisplayPort 드라이버의 Spec과 Subsystem 흐름을 분석하고, 모니터 재연결 시 화면이 나오지 않던 오류를 추적해 수정

과정텔레칩스 임베디드 SW스쿨
인원1명
대상DisplayPort 1.4 TX 드라이버
환경TCC805x · Linux

한 일

  • 20여 개 파일로 이루어진 드라이버의 호출 흐름을 StarUML·draw.io로 도식화
  • DisplayPort Spec과 DRM 서브시스템 흐름 분석
  • ftrace, dmesg, printk로 커널 로그와 드라이버 호출 구조 추적
  • 분석 결과를 매뉴얼로 정리

사용 기술

Linux KernelDevice DriverDRMftracedmesgprintk

트러블슈팅

모니터 재연결 시 화면이 나오지 않던 문제
문제 첫 연결은 정상이지만, 분리 후 다시 연결하면 링크 트레이닝 Clock Recovery 단계에서 "CR is not done" 반복
시도 성공 시 DPCD 값을 저장해 복구 → Fatal Error로 재부팅. DPCD는 모니터 쪽 상태라 되돌릴 대상이 아님을 확인. 이후 PHY 초기화 제거, 링크 속도 기본값, 지연 후 재시도로 원인 후보를 하나씩 제거
해결 링크 트레이닝 함수와 HPD 콜백에서 PHY를 다시 초기화
결과 분리·재연결을 반복해도 화면 정상 출력. 이후 분리 시 PHY를 직전 링크 속도로 리셋하지만 재연결 시 최대 속도로 트레이닝하는 구간이 있음을 코드로 확인

배운 점

증상을 되돌리기보다, 어디까지가 하드웨어 상태이고 어디부터가 드라이버 흐름인지 먼저 나눠야 원인에 닿는다는 것을 배웠습니다.
